# Running Injury Clinic (Calgary) Treadmill Running 3D Marker Trajectories Float64

- Candidate id: `ric_treadmill_running_marker_trajectories_f64`
- Width: float64
- Quantity: 3D lab-frame positions (mm) of the 28 rigid-cluster skin markers (pelvis, thighs, shanks and feet, 4 markers each) during treadmill running, captured with Vicon at 120 or 200 Hz. The values are full-precision doubles: the JSON uses 17-significant-digit repr, none of 420,000 checked values is float32-exact, and all are unique. The JSON field is 'running': {marker: [[x,y,z], ...]}. Neutral/joint static poses, descriptive variables (dv_r/dv_w) and the demographic/injury CSV metadata are not primary and must not be emitted.

- Natural record: One collection-session JSON (one subject visit) and its complete treadmill running trial, emitted as a frames × 28 markers × 3 float64 array. The probed session has 5,000 frames × 28 × 3 = 420,000 values. Uncompressed member sizes run 2.6–42.9 MB (median 16.6 MB, roughly 0.8M values). There are 2,506 session JSONs: 1,832 with running and 2,088 with walking. Proposal: about 80 running sessions evenly spaced over run_data_meta.csv order. Optionally the walking blocks of the same files can form a second primary series with identical semantics; that material is already downloaded.

- Decode path: Everything sits in one 22,749,955,646-byte ZIP64 (ric_data.zip). Range GET the 376,084-byte central directory at offset 22,749,579,464 through ndownloader with -L; it redirects to a fresh signed S3 URL each time. Parse the CD entries with struct (4,304 entries, 2,506 .json, all method 9 = Deflate64, CRC and sizes in the CD). Range GET each chosen member from its local-header offset to the next entry's offset. Wrap it in a synthetic one-entry ZIP (local header + CD + EOCD built with struct) and inflate it with `unzip -p`. Info-ZIP 6.0 here is compiled with USE_DEFLATE64, decoded an 8.3 MB member in 0.07 s and verified CRC. A pure-Python Deflate64 inflater (prototype tested on a 600 KB prefix) also works. Then json.loads, take data['running'][marker] lists, and struct.pack('<d') them in fixed marker order.
- Novelty kind: new_source
- Novelty evidence: novelty.py --url (figshare landing) --terms running injury clinic treadmill marker: no URL match. Mocap marker trajectories exist only at 32 bits: figshare_fukuchi_marker_trajectories_f32, a different dataset (PeerJ 2018 walking set, native C3D float32), and downstream walking_marker_x/y/z_f32. There is no biomechanics or motion-capture family at 64 bits locally, downstream, or among this effort's 15 accepted 64-bit families. The registry has no prior attempt on figshare+ 24255795.
- Homogeneity: One lab (University of Calgary Running Injury Clinic, 2009–2017), one marker protocol (Pohl et al. 2010 seven-segment clusters, the same 28 marker names), one unit (mm) and lab frame, and one activity (treadmill running). Two Vicon setups (3-camera Bonita or 8-camera MX3+) and two rates (120 or 200 Hz, stored in hz_r) occur. The builder can restrict to 200 Hz sessions or to sessions with the exact 28-marker set for strict homogeneity. Walking, if included, would be a separate series with the same semantics.
- Risks: Deflate64 members cannot be read by Python zlib/zipfile. The recipe depends on Info-ZIP unzip with Deflate64 support (present) or must ship a pure-Python inflater. The signed S3 redirect expires after 10 s, so every range request and retry must go back through ndownloader with -L. Some sessions may have a different marker count or null (NaN) entries, so the builder needs an explicit missing-value policy. The subject demographic/injury metadata must stay out of outputs (privacy). The data are de-identified under ethics approval, and marker trajectories alone are not identifying.
