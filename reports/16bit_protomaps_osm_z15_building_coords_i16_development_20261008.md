# Protomaps OSM z15 building vertex coordinates int16 development

## Outcome

Accepted `protomaps_osm_z15_building_coords_i16` from the dated Protomaps
planet basemap build `20250120.pmtiles` (basemap v4.0.4, generated by
planetiler from OSM replication 2025-01-20T04:00Z).

This is the first quantized vector-tile geometry in the corpus. Each sample is
the `buildings` layer of one zoom-15 Mapbox Vector Tile, decoded from the MVT
zigzag-delta command stream into absolute integer tile-space vertex
coordinates. Existing GIS vector geometry families store floating-point
lon/lat: Google Open Buildings f32 and Natural Earth f64. The nearest 16-bit
family by bytes is TrueType glyph coordinates (zlsim distance 0.0826, verdict
OK).

## Shape and conversion

`cities.tsv` lists 74 city centres on six continents. Each centre defines an
8x8 z15 tile block, aligned to multiples of 8 and nearest-centred on the city.
An aligned block is one contiguous Hilbert tile-id range, so in the clustered
archive its tile payloads form one byte span.

Build steps for each tile:

1. Resolve the tile through the root and leaf directories (PMTiles v3 varint
   directories).
2. Gunzip the tile and parse the protobuf.
3. Select the `buildings` layer, enforcing extent 4096 and MVT version 2.
4. Decode every polygon (GeomType 3) feature with a strict MoveTo/LineTo/ClosePath
   structure. The cursor starts at (0,0) for each feature, and ClosePath adds
   no vertex.
5. Write the interleaved x,y vertices as little-endian int16, one sample per
   tile.

Tiles are skipped, never merged, in these cases:

- absent from the archive
- payload deduplicated outside the block span (91 tiles)
- no buildings layer (294 tiles)
- fewer than 1,000 values (651 tiles)

The coordinates are the tile's own stored integers, so the series is
`native_numeric`. They are 14-bit signed values bounded by the extent plus the
64-unit buffer, so int16 is the honest width.

## Judge checks

- **Gate:** `gate.py` passes with no warnings.
- **Verify:** I ran `bash verify.sh` myself. It passed in 59 s: decoder
  self-test, every tile decoded again from the downloads and compared byte for
  byte, index fields, range, at least 50 distinct x and y per sample, no
  duplicate hashes, floors, and manifest totals.
- **Independent decode:** I wrote my own protobuf and MVT geometry decoder in
  /tmp, using the recipe only to locate tile slices. It matched the stored
  bytes for all 296 eligible tiles in 6 random blocks (Helsinki, London,
  Bangkok, Mexico City, Boston, Kampala). Below-floor tiles were confirmed
  absent from the index.
- **Tile locations:** names embedded in the tiles match their cities
  (São Paulo, Montevideo, London, Tokyo, Beijing, Dar es Salaam, Sydney).
  The Times Square tile 9649/12314 gives 1,686 features and 11,840 vertices,
  as the scout found.
- **Byte statistics:**
  - Edge values -64 and 4160 are 0.53% each (buffer clipping). Their share per
    sample is median 1.3%, max 6.1%. All other values are near-uniform at
    about 0.024%.
  - Consecutive-vertex |dx|: 0 in 4.9%, under 64 in 84.6%, 256 and up in 5.1%.
  - Repeated vertices: 0.12%.
  - Vertices per feature: median 6.5, min 4.0. Rings per feature: median 1.006.
  - All 3,700 sample hashes are unique.
- **Rights:** I opened the protomaps/basemaps README and the docs downloads
  page myself; the ODbL Produced Work statements are quoted above. The
  hotlinking caveat does not bear on a one-time bounded pull of about 150
  range GETs. No credentials appear in any script. No names, tags or
  contributor fields are emitted.
- **Novelty:** `novelty.py` (URLs build.protomaps.com,
  build-metadata.protomaps.dev, protomaps; terms protomaps, pmtiles, vector
  tile, mvt, openstreetmap) finds no other recipe, registry row or downstream
  family for this source or representation. The `gis_vector_geometry` type
  has only the f32 and f64 lon/lat families.
- **Breadth:** zlsim gives OK.
  - The nearest family is the glyf coordinates (local and downstream) at
    distance 0.0826. The local glyf compressor is compression-equivalent
    (loss -1.3%), but the distance is above the 0.05 redundancy threshold.
  - Other neighbours (LibriSpeech, FSDD, EHG) are at 0.088 or more with
    losses of 9.5% or more.
- **Reproducibility:** builds.json, fetched today, still lists 20250120
  (v4.0.4) with the pinned size.
