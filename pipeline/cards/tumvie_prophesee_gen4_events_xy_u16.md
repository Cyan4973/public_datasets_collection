# TUM-VIE Stereo Visual-Inertial Event Dataset: Prophesee Gen4 HD (1280x720) Event-Camera Pixel Address Streams (x, y) UInt16, Left Camera

- Candidate id: `tumvie_prophesee_gen4_events_xy_u16`
- Width: uint16
- Quantity: Per-event pixel coordinates of an event (DVS/CD) camera: x column in [0,1279] and y row in [0,719], stored natively as uint16 HDF5 datasets events/x and events/y (one entry per brightness-change event, ~15-27 M events/s). Event timestamps (int64) and polarity (u8) are other widths and stay out (t may be auxiliary).

- Natural record: One sequence's left-camera event stream (21 non-calibration sequences: mocap-1d-trans, mocap-3d-trans, mocap-6dof, mocap-desk, mocap-desk2, mocap-shake, mocap-shake2, office-maze, running-easy/hard, skate-easy/hard, loop-floor0..3, floor2-dark, bike-easy/hard/night, slide). Full streams are 0.57-7.8 G events each (1.2-17.9 GB per file, 168.7 GB total for left), so the recipe needs a bounded subset. Suggested: per sequence, 4 contiguous windows of 2^20 events (32 whole HDF5 chunks) at evenly spaced chunk offsets (or ms_to_idx-aligned time windows). Each window emits its x stream and y stream as separate primary uint16 samples of 1,048,576 values.
- Estimated samples: 168
- Estimated primary values: 176,160,768
- Estimated download bytes: 265,000,000
- Estimated primary bytes: 352,321,536
- Decode path: curl byte ranges only (Accept-Ranges: bytes confirmed): fetch the first ~1 MB for the superblock v0 (offset/length size 8), the v1 object headers and the symbol-table groups (/events/{p,t,x,y}, /ms_to_idx). Pure-Python parse: the layout message v3 class 2 (chunked, chunk dim 32768) points to a v1 B-tree type-1 chunk index (level 2 root, ~57 entries/node, 32-byte keys). Walk it with small range GETs to the leaf entries (chunk size, filter mask, offset, address). Each chunk is a Blosc1 container (HDF5 filter 32001; header flags 0x91 = byte-shuffle + DONT_SPLIT, compressor code 4 = ZSTD, typesize 2, nbytes 65536, blocksize 32768). For each block: int32 csize, then one zstd frame (magic 28b52ffd). Decompress with the zstd CLI (frames can be concatenated into one zstd -dc call), then unshuffle bytes (out[0::2]=lo, out[1::2]=hi) and unpack little-endian uint16. Same pattern as reusable sevir_hdf5.py v0/v1 helpers plus the MPC zstd-CLI precedent.
- Novelty kind: new_modality
- Novelty evidence: novelty.py --url https://tumevent-vi.vision.in.tum.de/ --terms prophesee tumvie: no URL, recipe, registry, ledger or downstream matches. The corpus has no event-camera/DVS material at any width (grep of datasets/*/manifest.toml for 'event camera|dvs|prophesee' is empty). Distinct from tum_rgbd_depth_u16 (different TUM dataset, sensor and quantity).
- Homogeneity: Single sensor model (Prophesee Gen4 CD 1280x720, left camera of the same stereo rig) and the same HDF5 layout and Blosc settings in every file (verified on mocap-1d-trans and bike-easy). x and y are separate series with fixed ranges (0-1279 and 0-719). Scenes vary (mocap room, office, running, skating, biking, night), but unit and scale are identical. Keep the right camera and the calibration sequences out, or treat them as a later extension.
- Risks: Decode complexity: v1 chunk B-tree traversal over HTTP plus Blosc/ZSTD needs the zstd CLI, the same dependency precedent as the MPC recipes. Window selection is a bounded sub-slice of very long streams; the judge must accept windowed slices as a coherent bounded subset (prefix/evenly-spaced windows), not tiling. Event addresses look noise-like in very active segments, but they are genuine pixel coordinates. The server is a university host (single origin); its large files and range support were verified.
