# GRACE-FO L1B RL04 hybrid-transplant accelerometer (ACH1B, GRACE D), float64

This recipe collects daily 1 Hz non-gravitational linear accelerations of
GRACE-FO 2 (GRACE D) from the JPL Level-1B RL04 product **ACH1B**, *GRACE-FO
Level-1B Hybrid Transplant Accelerometer Data*. Each sample is one UTC day of
the `lin_accl_x`, `lin_accl_y` and `lin_accl_z` columns (m/s², science
reference frame), stored as a native float64 `[records, 3]` array.

- Source (anonymous mirror): <https://isdc-data.gfz.de/grace-fo/Level-1B/JPL/INSTRUMENT/RL04/>
- Dataset page: <https://podaac.jpl.nasa.gov/dataset/GRACEFO_L1B_ASCII_GRAV_JPL_RL04>
  (DOI 10.5067/GFL1B-ASJ04; in-file id 10.5067/GFJPL-L1B04)
- License: NASA Earth Science open-data policy. Every ACH1B header carries
  `license: https://science.nasa.gov/earth-science/earth-science-data/data-information-policy`.
  That URL is now a 404. Its NASA Earthdata successor says: "data provided
  from a NASA-led mission are licensed as Creative Commons Zero (CC0)" and
  "there are no restrictions on the use of these data". The product is
  generated by NASA/JPL and published by PO.DAAC, so it is recorded as CC0-1.0.
  Cite the DOI.

## Material

| item | value |
| --- | --- |
| series | `gracefo_ach1b_lin_accl_srf_f64` (primary, the only series) |
| sample | `ACH1B_<YYYY-MM-DD>_D.f64le.bin`: 86,400 × 3 float64 = 2,073,600 bytes |
| layout | row-major; per 1 s epoch the triple (x, y, z) |
| samples | 97 days, 2023-01-01 .. 2026-06-28, every 12th ACX2 day |
| primary (realized) | 25,142,400 values, 201,139,200 bytes; all 97 days complete |
| download | 97 tarballs, 617,255,766 bytes |

Realized ranges over all 97 samples: X -1.25e-6..3.19e-7 m/s² (typically
-2e-7..3e-7; only 2024-08-13 and 2025-11-12 dip below -5e-7), Z
-2.98e-7..6.6e-8 m/s², Y 9.98e-6..1.093e-5 m/s². X and Z carry drag,
solar-pressure and orbital-period signal. Y sits on a ~1e-5 m/s² instrument
bias with small variations. Values are published as decimal ASCII with up to
16 significant digits. In every realized sample each component has 86,400
distinct values (index field `component_distinct_counts`). In the 7 probe days
checked for it, no value was exactly representable in float32.

## Why ACX2, and why not Q1 2023 of ACX

JPL ships the accelerometer products in daily `...ascii.ACX.tgz` tarballs and,
since 2024-09, in `...ascii.ACX2.tgz` tarballs. Probing ACH1B headers
(`history: INPUT FILE NAME : ACC1A<-XXXXX_<date>_D_04.dat`) showed that the
**ACX** line mixes several L1A input lineages under the same product name:

| ACX date | ACC1A input | software |
| --- | --- | --- |
| 2019-06-01, 2021-06-01 | ACC1A | V04.10.2020-11-09 |
| 2022-06-01 | ACH1A | V04.10.2020-11-09 |
| 2022-12-31 | ASO1A | V04.10.2020-11-09 |
| 2023-01-01, 2023-02-28 | AFO1A | V04.10.2020-11-09 |
| 2023-03-01, 2023-03-31 | ACH1A | V04.10.2020-11-09 |
| 2024-03-01 | ACT1A | V04.10.2020-11-09-82-gd120e-dirty |

The originally proposed window (ACX, 2023 Q1) therefore switched input lineage
on 2023-03-01. Residual statistics in the `.rpt` files also changed then
(~3e-8 vs ~7e-9 m/s²).

The **ACX2** line covers 2023-01..02, 2023-07..12 and everything from 2024
onward. It was the only line published from 2025 at discovery. In every ACX2
header probed (2023-01-01, 2023-02-18, 2023-07-15, 2023-08-31, 2023-12-31,
2024-06-15, 2024-12-15, 2025-06-15, 2026-06-15), ACH1B came from `ACH1A` with
software `V04.10.2020-11-09-82-gd120e-dirty`. The recipe uses ACX2 only, and
build fails if any selected file deviates from that input or software build.
The member taken is the same product, ACH1B; only the tarball line differs.

## Selection

`discover.sh` and `scripts/select_days.py` take every ACX2 tarball dated
2023-01-01..2026-06-30 (1,155 candidates), sort them by date and keep every 12th,
starting with the first. That gives 97 dates: 21 in 2023, 30 in 2024, 31 in
2025 and 15 in 2026. The end is fixed at 2026-06-30 because the 2026 listing
is still growing. ACX2 has no tarballs for 2023-03..06 (those days exist only
as ACX), so the stride skips that gap. The 97 files are pinned in
`sources.tsv` by name, size, Last-Modified, ETag and SHA-256. ISDC publishes
no checksums, so the SHA-256 values come from the first validated download
(2026-10-08).

## Decode

1. `download.sh` curls each tarball (resumable, stall-abort), checks its size
   and gzip magic, then runs `scripts/ach1b.py validate-downloads`.
2. `build.sh` streams each tarball with `tarfile` (`r|gz`). It md5-hashes every
   member and keeps only `ACH1B_<date>_D_04.txt` in memory. It then requires
   the tarball's `checksum` member (md5sum format) to list exactly the members
   present, with matching hashes. A missing ACH1B member is fatal.
3. The ACH1B header (everything up to `# End of YAML header`) is checked: title,
   `platform: GRACE D`, `product_version: 04`, id, license URL, ACH1A input
   for the same date, and software build. The column order comes from the
   header's `variables:` list, cross-checked against each `Nth column`
   comment. No index is hard-coded.
4. Each row is split on whitespace. The token count must match the declared
   variables, `GRACEFO_id` must be `D`, and `gps_time` must lie on the 1 s
   lattice of the UTC day and be strictly increasing. The row count must
   equal `num_records`. `lin_accl_x/y/z` are parsed with `float()` and must be
   finite with |a| < 1e-4 m/s².
5. Output is little-endian float64 `[records, 3]`. Index min/max come from the
   stored values.

Excluded columns: `ang_accl_*` (published as zero in ACH1B; nonzero rows are
counted per sample), `acl_*_res` (residuals against non-CRN-filtered values, a
model side product), `qualflg` (nonzero rows counted per sample, nothing
dropped), `gps_time` and `GRACEFO_id`. Excluded members: AC01B and AC11B
(thruster-model products for GRACE C and D), ACU1B (an updated transplant
that nearly duplicates ACH1B, present in the Jan–Feb 2023 ACX2 tarballs),
and the `.rpt` reports.

Partial days: absent lattice seconds are not filled. They are listed in the
index (`missing_seconds`), and a day with fewer than 43,200 rows is fatal. All 97
realized days are complete (86,400 rows each). `ang_accl_*` is zero on every
row of every day. `qualflg` is nonzero on 31.6% of rows overall (0..58k rows
per day). In the 7 probe days the dominant nonzero pattern is `00011000`
(bits 3 and 4: an extrapolated CLK1B clock offset was used inside the CRN
filter window). No rows are dropped.

`verify.sh` re-derives every sample independently. It reads the tarball
through random-access `tarfile`, re-checks the member md5, parses rows with a
regex, packs with `struct.pack('<3d')` and byte-compares with the stored file.
It also re-checks index fields, stored-dtype min/max, distinct counts,
nonconstancy, distinct hashes, manifest counts and floors.

## Breadth check

`tools/autocollect/zlsim.py gate` (2026-10-08) returned verdict **OK**, not
redundant. The family's own held-out compression ratio is 1.459. The nearest
families, given as (feature distance, compression loss), were:

- `orex_ola_l2_lidar_point_xyz_f64` (0.035, 6.8%)
- `naif_mro_sc_bus_attitude_ck_f64` quaternions (0.072, 21.9%)
- `gfz_gracefo_fgm_acal_bnec_f64` (0.085, 6.9%)
- `monado_msd_valve_index_imu_f64` gyro (0.092, 7.5%)

The redundancy rule needs both distance ≤ 0.05 and loss ≤ 3%. OREx is within
the distance threshold but not the loss threshold. Breadth is OK, not STRONG.

## Caveats

- ACH1B is a derived operational product (a hybrid transplant built from
  GRACE C accelerometer data for the degraded GRACE D instrument), not raw
  GRACE D sensor output. It is the pinned L1B product JPL distributes for
  gravity processing.
- The Y axis is dominated by a near-constant ~1.05e-5 m/s² bias, which differs
  in scale from X and Z. All three are one vector record, as in IMU xyz.
- Extraction ratio is about 2.07 MB kept per 6.1 MB tarball (11 MB for the 5
  Jan–Feb 2023 files), because the tarballs also carry thruster-model products.
- This is the second GFZ ISDC host recipe after `gfz_gracefo_fgm_acal_bnec_f64`
  (a different product: GFZ magnetometer CDFs).
